## Context

The repository is a pnpm + Turborepo monorepo with three deployable apps:

| App | Runtime | Port | Upstream Deps |
|-----|---------|------|---------------|
| `apps/frontend` | Next.js 15 | 7000 | `NEST_ORIGIN` → backend:3000 |
| `apps/backend` | NestJS 11 | 3000 | `LANGGRAPH_BASE_URL` → langgraph-server:8123 |
| `apps/langgraph-server` | LangGraph.js | 8123 | `DATABASE_URL` → langgraph-postgres:5432 |

All three share the workspace package `packages/api` (tRPC definitions). The deployment target is a k3s single-node cluster on the developer's machine. Each app will be built as a Docker image and pushed to GHCR. Deployment is handled via ArgoCD — the `k8s/` manifests in this repo are read by ArgoCD and auto-synced to the k3s cluster.

The CthuTool repository serves as the homelab management hub — its `gitops/` directory holds cluster-level configuration: namespaces and ArgoCD Application CRs for all deployed apps. See Decision 7 for the full architecture.

## Goals / Non-Goals

**Goals:**
- Docker images buildable for all three apps
- Each app has a `.dockerignore` that excludes non-runtime files
- k8s manifests for the full service topology (3 apps + 1 PG) deployable to k3s
- CI builds and pushes Docker images for all three apps on `main` push
- Zero new npm dependencies

**Non-Goals:**
- Docker Compose (local dev uses `pnpm dev`; deployment uses k3s)
- HTTPS / Ingress / TLS termination (ClusterIP only; Ingress is a separate concern)
- PostgreSQL high availability (single StatefulSet replica; no replication)
- Monitoring, alerting, log aggregation
- Helm chart or Kustomize overlays (plain YAML; upgrade path open)
- Auto-deployment / continuous delivery (images are built and pushed by CI; k8s sync is handled by ArgoCD via CthuTool's `gitops/`, not in this change)
- Production-grade secrets management (plain K8s Secrets with placeholder values)

## Decisions

### Decision 1: Dockerfile strategy per app

Three apps, three different strategies based on what each framework provides:

| App | Strategy | Dockerfile committed? | Rationale |
|-----|----------|----------------------|-----------|
| langgraph-server | `langgraph build` (CLI auto-generates) | No | LangGraph CLI reads `langgraph.json`, produces the image. Maintainer (LangChain) keeps it current with runtime changes. |
| backend | Hand-written multi-stage Dockerfile | Yes | NestJS has no CLI Docker generation. Standard Node.js multi-stage: deps install → tsc build → production image with `node dist/main.js`. |
| frontend | Hand-written multi-stage Dockerfile + Next.js `output: "standalone"` | Yes | Next.js standalone mode produces a self-contained directory trace with only production dependencies. The Dockerfile is multi-stage (monorepo deps → `next build` → copy standalone output). Also requires adding `output: "standalone"` to `next.config.ts`. |

**Why `output: "standalone"` for Next.js:**

Next.js's standalone mode (`output: "standalone"` in `next.config.ts`) is the framework's recommended Docker deployment path. When enabled, `next build` produces:

```
.next/
├── standalone/           ← Self-contained Node.js app
│   ├── server.js         ← Entrypoint (generated by Next.js)
│   ├── node_modules/     ← Only the production deps actually imported
│   └── ...               ← (includes workspace packages via tracing)
├── static/               ← JS/CSS/image assets
│   ├── chunks/
│   └── ...
```

The key mechanism is **output file tracing** — Next.js follows the `import` graph from every page and API route, copies only the `node_modules` that are actually used, and bundles everything into the standalone directory. The `outputFileTracingRoot` already set to the monorepo root (`path.join(__dirname, '../..')`) ensures workspace packages like `@pixel-playground/api` are included in the trace.

**Dockerfile structure for Next.js standalone:**

```dockerfile
# Stage 1: deps — install workspace dependencies
FROM node:24-alpine AS deps
RUN corepack enable && corepack prepare pnpm@9.15.9 --activate
WORKDIR /app
COPY pnpm-workspace.yaml .npmrc package.json pnpm-lock.yaml ./
COPY packages/api/package.json ./packages/api/
COPY apps/frontend/package.json ./apps/frontend/
RUN pnpm install --frozen-lockfile

# Stage 2: build — compile the app
FROM deps AS builder
COPY packages/api ./packages/api
COPY apps/frontend ./apps/frontend
RUN pnpm --filter @pixel-playground/frontend build

# Stage 3: runner — minimal production image
FROM node:24-alpine AS runner
WORKDIR /app
ENV NODE_ENV=production
COPY --from=builder /app/apps/frontend/.next/standalone ./
COPY --from=builder /app/apps/frontend/.next/static ./apps/frontend/.next/static
COPY --from=builder /app/apps/frontend/public ./apps/frontend/public
EXPOSE 7000
CMD ["node", "server.js"]
```

Note: `COPY --from=builder …/public` only copies if a `public/` directory exists (it does in this project per the langgraph-server's `static/` analogy). The standalone output places `server.js` at the root; `node server.js` starts the production Next.js server on `$PORT` (default 3000, overridden to 7000 via env).

**NestJS backend Dockerfile** follows the same pattern but simpler — no standalone mode, just `nest build` → `node dist/main.js`.

### Decision 2: k8s manifests directory structure

**Chosen**: `k8s/` at repo root, subdirectories per app/resource. The `namespace` resource lives in CthuTool's `gitops/` (cluster-level concern), not here:

```
PixelPlayground/k8s/
├── configmap.yaml              ← shared non-sensitive env vars for all apps
├── secret.yaml                 ← shared sensitive values (placeholders)
├── langgraph-server/
│   ├── deployment.yaml
│   └── service.yaml
├── langgraph-postgres/
│   ├── statefulset.yaml
│   ├── service.yaml
│   └── pvc.yaml
├── backend/
│   ├── deployment.yaml
│   └── service.yaml
└── frontend/
    ├── deployment.yaml
    └── service.yaml
```

**Alternatives considered**:
- **Flat directory** (`k8s/deployment-frontend.yaml`, `k8s/deployment-backend.yaml`, …): fine for 3 apps, becomes a mess at 10+. Subdirectories scale.
- **Per-app k8s directories** (`apps/frontend/k8s/`): scatters infra across the tree, harder to get a global view. Central `k8s/` at repo root gives ArgoCD a single `path` to point at.
- **Helm chart**: too much complexity for 3 apps with no environment variance yet.

**Rationale**: One `k8s/` directory gives a single `path` for ArgoCD's Application CR to target. Per-app subdirectories keep files focused. The namespace is a cluster-level resource — it belongs in CthuTool's `gitops/`, not in the app repo. ConfigMap and Secret live at the `k8s/` root because they're shared across all three apps within this namespace.

### Decision 3: PostgreSQL dedicated to langgraph-server

**Chosen**: A single PostgreSQL StatefulSet named `langgraph-postgres` in the `k8s/langgraph-postgres/` subdirectory, used exclusively by langgraph-server.

**Alternatives considered**:
- **One PG for all apps**: shared database reduces operational overhead but couples services — a backend migration could break the langgraph checkpointer. Separate databases per service is the established pattern for microservices.
- **External PostgreSQL** (outside k3s): separates concerns but adds operational complexity. For a single-node deployment, running PG inside k3s keeps everything under `kubectl`.

**Rationale**: LangGraph Server requires PostgreSQL for its checkpointer — it's a hard dependency. Backend and frontend don't currently need a database. If backend later needs one, a new StatefulSet (`k8s/backend-postgres/`) can be added without affecting the langgraph PG. Naming it `langgraph-postgres` makes the ownership explicit.

### Decision 4: CI docker job

**Chosen**: A single new `docker` job in `.github/workflows/ci.yml` that builds all three Docker images in parallel on `main` push, then pushes them to GHCR.

**Job flow**:
```
docker (main push only, needs: quality)
  │
  ├── checkout + setup pnpm + setup Node
  ├── install deps
  │
  ├── [parallel]
  │   ├── Build langgraph-server  (langgraph build)
  │   ├── Build backend           (docker build -f apps/backend/Dockerfile)
  │   └── Build frontend          (docker build -f apps/frontend/Dockerfile)
  │
  └── [sequential]
      ├── Login GHCR (docker/login-action)
      └── Push all images (sha-<hash> + latest tags)
```

**Why `main` push only, not PRs**: Docker builds take minutes. PR feedback is already covered by lint + tsc build + tests in the `quality` job. Running Docker builds on PRs would slow CI without adding signal — if the TypeScript compiles and the Dockerfile is hand-written (not generated), the Docker build will succeed barring a COPY path error, which is rare.

**Why parallel builds**: Each app's Docker build is independent. Building them sequentially would triple the job time with no benefit.

**Image tagging**: `ghcr.io/mickmetalholic/pixelplayground/<app>:sha-<7-char-hash>` and `ghcr.io/mickmetalholic/pixelplayground/<app>:latest`. The SHA tag enables immutable references and rollbacks; `latest` is for convenience in dev.

### Decision 5: Kubernetes Secret management

**Chosen**: Plain Kubernetes `Secret` resources with base64-encoded placeholder values committed to the repo. Real values are applied during deployment.

**Why not sealed-secrets / sops / Vault**: All three require additional tooling and configuration. For a single-node self-hosted cluster with one operator, plain Secrets with explicit deployment steps are sufficient. The `secret.yaml` file includes comments explaining how to encode real values.

**Mitigation**: The `secret.yaml` contains only placeholder values. The file is committed so the structure is documented and ArgoCD can sync the Secret resource. Before first deployment, the operator replaces the placeholder base64 values with real ones and commits the change (or creates the Secret manually once outside of ArgoCD management).

### Decision 6: `.dockerignore` content (all three apps)

Common exclusions across all three apps:

| Entry | Reason |
|-------|--------|
| `node_modules` | Rebuilt inside Docker |
| `dist` | Rebuilt inside Docker |
| `.turbo` | Turborepo cache |
| `.git` | Git metadata |
| `*.md` | Documentation |
| `.env` / `.env.example` | Env templates (use k8s ConfigMap/Secret at runtime) |
| `.gitignore` | Git config |

Per-app additions:

| App | Extra exclusions |
|-----|-----------------|
| langgraph-server | `tests/`, `scripts/`, `jest.config.js`, `tsconfig.json` |
| backend | `tests/` (if any), `vitest.workspace.ts`, `tsconfig.json`, `tsconfig.build.json`, `nest-cli.json` |
| frontend | `tests/` (if any), `vitest.config.ts`, `vitest.setup.ts`, `tsconfig.json`, `tsconfig.tsbuildinfo`, `postcss.config.mjs`, `tailwind.config.*`, `components.json` |

**Kept in context**: `src/`, `package.json`, `static/` / `public/`, lockfile (at root level), and for frontend: `next.config.ts` (needed by `next build`).

### Decision 7: GitOps architecture — app repo vs CthuTool (homelab hub)

**Chosen**: Split responsibility between two repositories. CthuTool is the homelab management hub — its `gitops/` directory centralizes all cluster-level configuration:

| Repository | Role | Holds | Managed by |
|------------|------|-------|-----------|
| PixelPlayground | App repo | Dockerfiles, CI, `k8s/` (app-level manifests: Deployments, Services, StatefulSet, ConfigMap, Secret) | Developer + CI |
| CthuTool | Homelab hub | `gitops/` (namespaces, ArgoCD Application CRs, bootstrap), `apps/` + `packages/` (own application code) | Developer |

Data flow:

```
push to PixelPlayground main → CI builds images → pushes to GHCR
                                                     │
ArgoCD polls CthuTool gitops/apps/pixel-playground/ ─┘
  → reads Application CR → points to PixelPlayground/k8s/
  → ArgoCD auto-syncs PixelPlayground manifests to k3s

CthuTool's own backend deployment (future):
  → ArgoCD polls gitops/apps/cthutool/ → points to CthuTool/k8s/
```

**Why CthuTool as the homelab hub, not a separate repo**:
- CthuTool is already the "meta" project — it contains tools, Obsidian plugins, and the backend. Adding `gitops/` is a natural extension of its role.
- Fewer repos to manage. One `gitops/` directory gives a single view of all cluster workloads.
- When PixelPlayground or any future app repo needs deployment, its Application CR lives in CthuTool's `gitops/apps/<name>/`.

**Why not put everything in PixelPlayground**:
- Namespace is a cluster-scoped resource. If PixelPlayground is deleted, the namespace should survive (other apps may share it).
- ArgoCD Application CRs reference PixelPlayground from the outside — they're about the app, not part of the app.
- Other app repos shouldn't depend on PixelPlayground's repo structure.

**Why not auto-deploy from CI (push-to-deploy)**:
- CI has cluster credentials → security risk. ArgoCD pulls from inside the cluster → no external access needed.
- CI only knows "build succeeded." ArgoCD knows "cluster state matches git" and auto-heals drift.
- Git is the single source of truth for desired state. CI is just the image factory.

**What goes where — decision boundary**:

| Resource | PixelPlayground `k8s/` | CthuTool `gitops/` |
|----------|------------------------|---------------------|
| Deployment, Service | ✅ | |
| StatefulSet, PVC | ✅ (langgraph-postgres) | |
| ConfigMap | ✅ (app env vars) | |
| Secret | ✅ (app credentials, placeholders) | |
| Namespace | | ✅ |
| ArgoCD Application CR | | ✅ |
| Ingress, cert-manager | | ✅ (future) |
| Monitoring, ResourceQuota | | ✅ (future) |

**Rationale**: This is the minimal GitOps split. The app repo owns everything needed to run the app. CthuTool's `gitops/` owns everything about *where and how* apps run in the cluster. The boundary is: if deleting the app repo should leave the resource behind, it belongs in CthuTool's `gitops/`.

## Risks / Trade-offs

- **[Risk] `langgraph build` CLI behavior changes**: A future `@langchain/langgraph-cli` update could change the generated Dockerfile or base image in a breaking way. → **Mitigation**: Version pinned in `devDependencies`; CI catches breakage on the next `main` push after `pnpm update`.
- **[Risk] Next.js standalone mode misses a dynamic import**: Next.js can't trace `require(variable)` or dynamic `import(variable)`. If future code adds runtime-computed imports, the standalone output will be missing that dependency. → **Mitigation**: The current codebase uses only static ES imports. A CI step could smoke-test the built image to catch this early (not in scope for this change, but the foundation is laid).
- **[Risk] PG data loss on PVC deletion**: If the PVC YAML is deleted or the namespace is removed, data is gone. → **Mitigation**: `langgraph-postgres/pvc.yaml` has a clear comment warning against deletion without backup. Backups (pg_dump cron or Velero) are out of scope but the StatefulSet + PVC pattern is the standard foundation for adding them.
- **[Trade-off] Single PG replica**: No high availability, no read replicas. → Acceptable for a small self-hosted deployment. The StatefulSet can be upgraded to multi-replica or replaced with a managed PG service without changing the langgraph-server config — just update `DATABASE_URL`.
- **[Trade-off] No image tag strategy beyond sha + latest**: No semver or release-based tagging. → Acceptable for now; the SHA tag provides traceability to the exact commit. Release tagging can be added when the APIs stabilize.
- **[Trade-off] Secret placeholder values in a committed file**: Anyone with repo access can see the Secret structure, and if ArgoCD syncs the placeholder Secret before real values are substituted, the cluster will have invalid credentials. → **Mitigation**: The operator must replace placeholder base64 values in `secret.yaml` before ArgoCD's first sync. ArgoCD only reads manifests from git — it doesn't apply arbitrary changes. The CI never applies k8s manifests (only builds images).
